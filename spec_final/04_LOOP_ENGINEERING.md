# 九立新流程 Demo · Loop Engineering 执行协议

> 版本：v1.0 Final  
> 日期：2026-09-18  
> 用途：规定 Codex 如何围绕 Spec 连续执行开发闭环，避免“写一点代码就算完成”或“无限自主重构”。

---

# 1. Loop Engineering 的目标

这里的 Loop 不是简单重复运行命令。

真正闭环是：

```text
理解目标
→ 检查当前实现
→ 找到差距
→ 制定本轮最小方案
→ 实现
→ 自动测试
→ 业务场景验收
→ 分析失败
→ 修复
→ 再验证
→ 更新开发状态
→ 自动进入下一个未完成任务或停止
```

AI 的价值不是代替普通脚本，而是每一轮都能根据测试和业务验收结果决定“哪里还没达到 Spec”。

---

# 2. 默认执行粒度

每个 Loop 仍只完成一个 Task，但当前项目默认采用连续 Task 模式：

> **一次 Loop 只完成一个 Task。**

一个 Task 验收通过并更新 `DEV_STATUS` 后，自动读取下一个未完成 Task；不需要用户再次发送“开始下一个 Task”。

例如：

```text
TASK-0303：委托资料更新原草稿
```

允许该 Task 内自动：

- 阅读相关代码；
- 修改多个必要文件；
- 补测试；
- 运行测试；
- 修复失败；
- 再运行；
- 更新 DEV_STATUS。

完成后判断是否存在下一个未完成 Task。若当前 Phase Gate 已通过，则自动进入下一 Phase；若所有开发 Task 已完成，则停止并汇报。

---

# 3. 每轮必须读取的上下文

不是每次把全项目所有文件重新读一遍。

每轮至少读取：

1. `AGENTS_九立新流程Demo_v1.1_Final.md`；
2. `spec/00_SPEC_INDEX.md`；
3. `spec/DEV_STATUS.md`；
4. 当前 Task 所属的 `03_DEVELOPMENT_PLAN.md` 片段；
5. 当前能力对应的 `01_IMPLEMENTATION_SPEC.md` 片段；
6. 对应的 `02_SCENARIO_ACCEPTANCE_SPEC.md` Case；
7. 与当前 Task 直接相关的现有代码和测试。

只有发现规则冲突或上下文不足时，再回读产品需求 / Demo Final。

---

# 4. Loop 八步法

## Step 1｜确定当前 Task

从 DEV_STATUS 读取：

- 当前 Phase；
- 当前 Task；
- 已完成 Task；
- 当前阻塞。

如果 DEV_STATUS 不存在：

> 先执行 Phase 0，创建它。

如果当前 Task 已经完成，不重复开发，选择当前 Phase 下一个未完成 Task。

---

## Step 2｜先诊断，不直接改代码

Codex 在内部先完成：

```text
Spec 目标是什么？
现有代码已经有什么？
缺口是什么？
需要修改哪些文件？
需要新增哪些测试？
如何证明完成？
```

开始修改前应在本轮汇报或工作记录中形成一个简短计划：

```text
目标：
当前差距：
计划修改：
验收 Case：
预计运行测试：
```

避免先写大量代码后才发现业务理解错误。

---

## Step 3｜做最小完整实现

“最小”不是只改 UI。

最小完整实现必须同时覆盖当前 Task 所需的：

- 数据；
- 业务动作；
- 状态变化；
- 必要页面；
- 必要测试。

禁止为未来可能需求提前搭复杂抽象。

---

## Step 4｜运行自动检查

优先使用项目已有脚本。

至少覆盖等价能力：

1. TypeScript 类型检查；
2. 代码检查；
3. 当前 Task 相关 Vitest；
4. 必要时 Playwright；
5. 生产构建，若当前改动可能影响构建。

不要机械地每次跑所有昂贵测试；但当前 Task 的直接相关测试必须跑。

---

## Step 5｜按业务场景验收

自动测试通过不代表业务完成。

必须读取当前 Task 对应的 CASE，逐项确认：

```text
初始状态对吗？
操作真的经过业务动作了吗？
应该变化的对象都变了吗？
不该变化的对象保持了吗？
页面同步了吗？
版本 / 操作记录有了吗？
有没有违反业务不变量？
```

例如“改配”验收不能只检查按钮成功，而要同时检查：

```text
旧查货商品释放
旧关系失效但保留
新查货商品占用
新关系建立
委托字段刷新
新版本产生
操作记录产生
```

---

## Step 6｜自动修复失败

如果测试或场景验收失败：

```text
定位失败原因
→ 判断是实现错误、测试错误还是规则未知
```

### 实现错误

允许自动修复并重跑。

### 测试错误

只有当测试明确与 Final Spec 冲突时才能修改测试，并说明原因。

### 规则未知

禁止猜测。

写入 `OPEN_QUESTIONS.md` 并停止相关分支。

---

## Step 7｜重跑验证

每次修复必须重新执行：

- 失败的最小测试；
- 当前 Task 的关键业务验收。

如果修复可能影响共享状态，再跑相关回归测试。

---

## Step 8｜更新 DEV_STATUS 并决定继续或停止

Task 完成后记录：

- 完成了什么；
- 修改了哪些文件；
- 哪些测试通过；
- 哪些 Case 通过；
- 当前剩余限制；
- 是否新增 OPEN QUESTION；
- 下一 Task 是什么。

更新后按以下顺序处理：

1. 当前 Task 已完成且存在下一个未完成 Task：自动继续下一个 Task；
2. 当前 Phase Gate 已通过且下一 Phase 仍有未完成 Task：自动进入下一 Phase；
3. 所有计划中的开发 Task 均已完成：停止并汇报，等待用户验收或新需求；
4. 出现规则未知、同一问题连续 3 轮无法修复、真实样本需修改或用户要求暂停：停止并报告原因。

---

# 5. 自动修复次数与停止条件

同一问题默认最多自动尝试 3 轮修复。

```text
实现
→ 验证失败
→ 修复1
→ 失败
→ 修复2
→ 失败
→ 修复3
```

3 轮后仍失败：

> 停止并报告，不继续扩大改动范围。

以下任一情况必须立即停止：

1. 发现 Final 文档没有定义且影响业务结果的规则；
2. 需要修改真实业务样本才能让测试通过；
3. 需要推翻已通过的上一 Phase 核心模型；
4. 发现产品需求 Final 与 Demo Final 存在无法自行裁决的直接冲突；
5. 需要新增真实生产基础设施才能继续，而 Demo Spec 明确不要求；
6. 全部计划中的开发 Task 已达到完成定义。

---

# 6. OPEN_QUESTIONS 处理协议

Codex 首次运行时如果不存在则创建：

```markdown
# OPEN QUESTIONS

## Q-001｜问题标题

状态：待确认
发现于：TASK-xxxx

### 问题
具体缺失规则是什么？

### 为什么阻塞
不确认会导致哪两种不同实现？

### 已知资料
- 产品 Final：...
- Demo Final：...
- 当前代码：...

### 当前临时行为
没有明确规则时当前实现如何安全退化；如果无法安全退化，写“暂停该分支”。

### 需要用户确认
请在可选项中明确选择，或给出新规则。
```

确认后：

1. 更新权威 Spec；
2. 将问题状态改为“已解决”；
3. 写明最终规则；
4. 再继续对应 Task。

禁止只在聊天里确认后直接改代码而不更新文档。

# 7. DEV_STATUS 维护协议

建议固定结构：

```markdown
# DEV STATUS

更新时间：
当前 Phase：Phase X
当前 Task：TASK-XXXX
总体状态：进行中 / 阻塞 / Phase Gate 待验收 / 已完成

## 已完成 Task
- [x] TASK-0001 ...

## 当前 Task
- [ ] TASK-xxxx

## 当前验收
- CASE-xx：通过 / 未通过

## 测试基线
- 类型检查：通过 / 失败
- 代码检查：通过 / 失败
- 单元测试：xx/xx
- E2E：xx/xx
- 构建：通过 / 未运行 / 失败

## 本轮修改
- file...

## 当前阻塞
无 / Q-xxx

## 已知限制
- ...

## 下一 Task
TASK-xxxx
```

DEV_STATUS 是“进度事实”，不是业务规则文档。

---

# 8. Task 完成定义

一个 Task 只有同时满足以下条件才能打勾：

```text
实现代码完成
+
相关自动测试通过
+
对应 Scenario Case 通过
+
没有违反业务不变量
+
DEV_STATUS 已更新
```

“页面能点”“没有报错”“代码写完”均不等于完成。

---

# 9. Phase Gate 执行

完成当前 Phase 所有 Task 后，先执行 Phase Gate，再决定是否进入下一 Phase。

Phase Gate 检查：

1. 运行该 Phase 规定的关键测试；
2. 运行对应 Case；
3. 检查本 Phase 新增的业务不变量；
4. 检查是否遗留阻塞问题；
5. 更新 DEV_STATUS 为“Phase Gate 通过”。

Phase Gate 通过后自动进入下一 Phase 的第一个未完成 Task。只有出现第 8 步规定的停止条件时才暂停。

---

# 10. 两种 Loop 模式

## 10.1 默认模式：连续 Task Loop

适合日常开发。

用户指令：

```text
继续当前开发 Loop。
```

Codex：

- 完成一个 Task；
- 自动修复；
- 验收；
- 更新状态；
- 自动开始下一个未完成 Task。

---

## 10.2 连续模式：全项目开发 Loop

当前项目默认开启。用户也可以用以下指令恢复：

```text
连续完成全部开发 Task。
```

Codex 可以：

```text
Phase 1 Task 1 完成
→ Phase 1 Task 2
→ Phase 1 Gate
→ Phase 2 Task 1
→ ...
→ 全部 Task 完成
...
```

但：

- 每个 Task 都必须独立测试；
- 遇到规则未知或 OPEN QUESTION 立即暂停相关分支并报告；
- Phase Gate 通过后自动进入下一 Phase；
- 同一问题最多自动修复 3 轮；
- 全部 Task 完成后停止。

---

# 11. 不允许的“伪 Loop”

以下都不算 Loop Engineering：

## 11.1 只反复运行测试

```text
npm test
npm test
npm test
```

没有根据失败分析和修复，不是 Loop。

## 11.2 只让 AI 不断“优化代码”

没有 Spec、Case、停止条件，会无限重构。

## 11.3 自动把测试改到通过

测试是验收工具，不是障碍。

如果实现不符合业务，不允许把断言改弱。

## 11.4 页面通过就宣布完成

九立 Demo 的核心是业务状态，不是静态视觉。

# 12. Codex 初始化总指令

第一次正式开始 Spec Coding 时复制：

```text
你现在进入九立新流程 Demo 的 Spec Coding 模式。

先不要大规模开发。

必须先阅读：
- 产品需求 Final
- Demo 需求 Final
- 委托书草稿单模版.xlsx
- AGENTS
- spec/00_SPEC_INDEX.md
- spec/01_IMPLEMENTATION_SPEC.md
- spec/02_SCENARIO_ACCEPTANCE_SPEC.md
- spec/03_DEVELOPMENT_PLAN.md
- spec/04_LOOP_ENGINEERING.md

然后：
1. 检查当前仓库与 package.json；
2. 识别技术栈、已有页面、已有状态层、已有测试；
3. 扫描“真实整单样本”但保持只读；
4. 创建或更新 spec/DEV_STATUS.md；
5. 创建或更新 spec/OPEN_QUESTIONS.md；
6. 根据开发计划判断当前 Phase；
7. 从当前 Phase 的第一个未完成 Task 开始，完成后自动继续下一个未完成 Task；
8. 开始前先说明当前目标、代码现状、差距、计划修改文件和对应验收 Case；
9. 完成实现后自动运行相关检查与测试；
10. 按对应 Scenario Case 做业务验收；
11. 失败时最多自动修复 3 轮；
12. 规则未知时记录 OPEN_QUESTIONS，不得自行发明；
13. 完成 Task 后更新 DEV_STATUS 并自动继续；全部 Task 完成或触发停止条件后停止。

现有代码行为不能覆盖 Final Spec。
不要为了赶 UI 绕过业务动作层。
不要修改真实整单样本制造演示结果。
```

# 13. 日常继续开发指令

用户以后只需说：

```text
继续当前开发 Loop。
读取 spec/DEV_STATUS.md，从当前下一个未完成 Task 开始连续执行后续 Task。
按 04_LOOP_ENGINEERING.md 执行完整闭环：诊断 → 实现 → 测试 → 场景验收 → 必要修复 → 再验证。
满足 Task 完成定义后更新 DEV_STATUS 并自动继续；全部 Task 完成、明确阻塞或用户要求暂停时停止。
```

---

# 14. 指定 Task 开发指令

```text
执行 TASK-XXXX。

先读取该 Task 对应的 Implementation Spec 和 Scenario Case，检查现有代码差距，再做最小完整实现。

实现后必须跑相关自动测试并逐项验证 Case 的：
- 应变化内容；
- 不应变化内容；
- 页面联动；
- 版本 / 操作记录；
- 业务不变量。

最多自动修复 3 轮。完成后更新 DEV_STATUS；按连续开发模式自动继续下一个未完成 Task。
```

---

# 15. Bug 修复 Loop 指令

```text
进入 Bug Loop，仅处理当前问题，不扩大需求。

1. 先稳定复现；
2. 找到最小根因；
3. 补一个能够失败的回归测试；
4. 做最小修复；
5. 重跑该测试；
6. 重跑可能受影响的业务 Case；
7. 确认没有破坏业务不变量；
8. 更新 DEV_STATUS；
9. 停止。
```

---

# 16. Phase 验收指令

```text
不要开发新功能。现在只做当前 Phase Gate 验收。

读取 DEV_STATUS 和 Development Plan 中当前 Phase 的 Gate：
1. 运行要求的自动测试；
2. 执行对应 Scenario Case；
3. 检查业务不变量；
4. 汇总失败项；
5. 对明确实现错误允许修复并重验；
6. 规则未知则写 OPEN_QUESTIONS 并停止；
7. 全部通过后把 DEV_STATUS 标记为 Phase Gate 通过。

不要自动进入下一 Phase。
```

---

# 17. Demo 最终验收 Loop 指令

```text
进入 Final Demo Validation，不新增需求。

按 02_SCENARIO_ACCEPTANCE_SPEC.md：
- 跑完整主演示 E2E；
- 跑客户隔离；
- 单 PDF 多入仓号；
- 查货三键合并；
- 合并商品部分占用；
- 委托先到 / 查货后到；
- 委托资料更新；
- 多候选；
- 字段冲突；
- 人工改配；
- 提交人工确认；
- 确认完成与核销；
- 25 列最终结果；
- 多对多。

每个失败都要归类为：实现错误 / 测试错误 / 规则未知。
明确实现错误可修复后重跑；规则未知必须停止等待确认。
最终输出一份 PASS / FAIL 清单和剩余风险，不进行无关重构。
```

# 18. Codex 每轮最终汇报格式

每轮结束只需要清楚回答：

```text
当前 Task：
结果：完成 / 阻塞

实现：
- ...

修改文件：
- ...

验证：
- 类型检查：
- 单元测试：
- E2E：
- Scenario：

业务不变量：
- ...

新增问题：
- 无 / Q-xxx

DEV_STATUS：已更新

下一 Task：
- ...
```

不要用大段“我做了很多优化”的泛化描述代替可验证结果。
